## 敏感数据数据流(SSH 密码 / 私钥口令 / SMTP 密码,已审计闭环无泄漏)

```
前端密码框(type=password)
  → invoke('encrypt_password', {plain})      # SSH 密码唯一一次明文过 IPC
  → Rust: windows-dpapi encrypt(CurrentUser) → base64
  → servers.json 的 auth.password_enc(密文落盘)
运行期:
  前端始终传 password_plain: null(或临时输入)
  → 后端 resolve_password:dpapi_unprotect(password_enc) → 内存瞬时明文 → SSH 认证

私钥口令(阶段三,key_pass_enc):服务器表单输入(不回显)
  → 「记住口令」勾选:连接成功后 DPAPI 加密存 auth.key_pass_enc;不勾=仅本次连接使用,不落盘
  → 运行期 resolve_key_passphrase:dpapi_unprotect(key_pass_enc) → SshClient::connect 透传
    load_secret_key(key_path, passphrase);口令错误 → 中文映射「私钥口令错误或私钥已损坏」

SMTP 密码(阶段二,notify.json 的 email.password_enc):通知中心表单输入
  → notify_save_config:非空明文 → dpapi_protect 落盘;留空 → 保留已存密文
  → 查询脱敏:notify_get_config 只回 passwordSaved 布尔值,明文/密文都不出后端
  → 发送时 resolve_email_password 解密(内存瞬时);发信经 lettre(内存拼接,不落日志)

不变量:
  - 不存在解密命令;dpapi_unprotect 仅在 resolve_password / resolve_key_passphrase /
    config_io(导出解密→导入重加密)/ notify(SMTP 密码)内部调用
  - 明文/密文不进日志、不进事件、不进 localStorage、不进错误信息
  - **get_config 密文最小化(第十八批)**:返回密文哨兵 `"*"` 的只读视图(真实密文不出
    后端,`Some("*")` 保留「已存」语义);服务器编辑保存走 `save_server_entry`(密文/指纹
    传 null 由后端 merge 保留);`save_config_cmd` 仅用于配置中心导入等自带密文场景
  - **哨兵绝不落盘(v6.1.1 补丁,后端不变量)**:v6.0.0 只改 save_server_entry、漏掉
    4 条「get_config 全量取 → save_config_cmd 全量写回」路径(删服务器/删项目/保存项目/
    导入 compose/保存分类),哨兵被写进磁盘冲掉全部真实密文(用户真机报「Invalid symbol
    42」)。现 save_config_cmd/save_server_entry 均按 id 与磁盘现值合并,`"*"` 一律还原为
    现值(读不到现值降级 None,绝不写 `"*"`);`resolve_password`/`resolve_key_passphrase`
    对哨兵/非 base64 密文提前给可操作报错。**纪律:哨兵改造必须封死全部写回通道,还原
    责任放后端而非调用方约定**
  - DPAPI CurrentUser 作用域:同机同用户才可解;直接拷贝 config/ 到其他机器后密码必须重录
    (跨机器迁移用「配置中心」导出/导入:blob 内为口令加密的明文,导入时本机重新 DPAPI 加密)
```

## 配置导出加密格式(阶段三,config_io.rs)

```
文件 = JSON 信封 {"version":1, "kdf":"argon2id", "salt_b64", "nonce_b64", "data_b64"}
密钥  = Argon2id(导出口令, salt 16B 随机;Params::default: m=19MiB, t=2, p=1)→ 32 字节
data  = AES-256-GCM(认证加密,nonce 12B 随机)的明文 JSON:
        {"servers":[...], "projects":[...], "notify":{...}}
        blob 内 SSH 密码/私钥口令/SMTP 密码为明文(可移植),靠信封加密保护
导入口令错误 / 文件被篡改 → GCM 标签校验失败,统一报「导出口令错误或文件已损坏」(二者不可区分,有意为之)
导出口令不入文件;丢失口令 = 数据不可恢复(无后门)
```

## 远程操作互斥(第二十二批:后端不变量)

**同一时刻只允许一个远程操作**(部署 / 断点续传 / 一键回滚 / 回滚中心 / 项目迁移 / 镜像迁移 / **定时部署**)处于执行期——`commands/mod.rs` 的
`REMOTE_OP_IN_FLIGHT`(AtomicBool)+ `RemoteOpGuard`(RAII,Drop 释放)收口。

- 背景:互斥此前完全在前端(`window.ddRemoteOp` + `st.deploying`);定时部署
  是首个**后端自主发起**的部署方,没有前端动作可依赖,而后端所有管线共享
  同一份 `DeployState.cancelled` 取消位 —— 并发时后发起方的 `reset_cancelled`
  会吞掉先发起方的取消意图。
- 拒绝行为:统一文案「已有远程操作进行中(部署/回滚/迁移),请等待其完成
  后再试」;部署类被拒时按路径表达(单发/续传 emit 恰好一次
  `deploy-done` 失败帧;定时任务写 `last_result` 跳过);回滚/迁移类命令
  直接返回 Err(前端 toast 原文)。
- 已知边界:互斥为**进程内**;多实例(理论上用户可开两个 exe)不受保护
  ——单用户桌面场景接受(与配置写锁同边界)。

## 主机密钥:TOFU 校验(阶段三实现,原「无条件接受」安全债已清)

`ssh.rs` 的 `ClientHandler::check_server_key` 按 per-server 指纹校验(UPGRADE-PLAN 风险声明修改点 1):

- **指纹口径**:OpenSSH 风格 `SHA256:` + base64(nopad)(SHA-256(公钥 SSH wire blob)),与 `ssh-keygen -lf` 一致(russh 的 `PublicKey::fingerprint` 补前缀)
- **首次连接**(配置 `host_key_sha256` 为 None):接受并把观察到的指纹交由命令层 `persist_host_key_if_needed` 落盘(TOFU 信任-on-first-use;连接失败路径不落盘)
- **已有记录且匹配** → 接受
- **不匹配** → 拒绝连接,固定文案:「服务器主机密钥已变更!可能为服务器重装/换 IP,也可能存在中间人风险。如确认无误,请在服务器管理中重新信任该主机。」
- **重置**:03 服务器管理每服务器展示当前指纹(等宽)+「重新信任」按钮 → `retrust_host_key` 清空记录(二次确认),下次连接重新 TOFU
- 部署主线与远程管理全部建连路径(commands.rs 与 manage.rs 的 `connect_server`)统一接入;指纹记录随配置中心导出/导入迁移

    **不阻断**;④**回不去**(ID 真丢失,或旧归档无 ID 记录)→ 预检逐条列出并**要求用户确认**,
    确认后部分回滚(这些服务沿用服务器当前镜像)。**自动回滚恒不部分回滚**。
53. ~~回滚确认后无声失败~~ **已修复**(v6.11.0):此前缺包服务被静默跳过、`compose up -d` 用
    服务器当前镜像成功启动、**界面报「回滚完成」而服务并未回退** —— 是本轮 UX 审查发现的
    最严重的误导路径(用户以为安全、实际不安全)。现由预检(52)显式暴露。
54. 回滚**不恢复 `.env`**(v6.11.0 起归档 override,`.env` 刻意不入):`.env` 是环境变量,
    回滚它可能把密钥退回旧值,且服务器上本就保有明文。**影响**:若新旧版本的 `.env` 变量集
    不同,回滚后可能出现变量缺失/取值不符,需用户自行核对(`override` 文件不受此限,已随归档恢复)。
    **v6.12.0 补上检测**:compose 的 `image: ${VAR}` 由 up 当时的 `.env` 解析,而 manifest 的
    `tag` 正是部署当时的插值结果 —— 预检用「归档 compose + 服务器当前 `.env`」重算并逐条比对,
    漂移项(含变量被删/新增)列出「归档记录 X;按当前 .env 会解析成 Y」,**须确认后才执行**,
    确认后按实际解析结果启动并留痕。判定基准复用 manifest 的 tag,**不新增字段、旧归档同样可检**。
    同一检测在部署侧用于 up 后校验(容器实际镜像 ≠ 本次构建即告警)。
55. **执行期 TOCTOU 的剩余窗口**(v6.12.0 明确其边界):预检/跳过判定都只是**查询那一刻**的快照,
    而 up 一律按 compose 的 `repo:tag` 解析 —— 中间隔着逐包 `docker load`(秒级到分钟级),
    外部主体(另一台机器的本应用 / CI / 运维脚本)改标签会让结论失效(本应用互斥锁只锁本进程)。
    v6.12.0 的「按镜像 ID 收敛」步把窗口压到「收敛查询 → up」这一小段,up 后校验再兜底**发现**;
    **v6.16.0 起另有 up 前「服务端权威解析校验」**(`docker compose config` 的解析结果与
    记录逐服务比对;部署阻断 / 回滚告警,见决策 87)—— 收敛治标签指向、本校验治解析结果,
    两处互补仍非事务性;
    不追求零窗口(Docker 不提供「tag 后立即 up」的事务语义)。部署侧同样接入(期望值 = 本次本地
    采集 ID;**拉取类服务不参与** —— 其 tag 语义就是要随 pull 移动)。
56. 回滚**无断点续传**:`rollback.rs` 不含 checkpoint 机制(与部署管线不同)。中断后残留状态
    可能是「部分包已 load」/「compose 已覆盖未重建」/「up -d 执行到一半」。**恢复路径 =
    重新发起同一次回滚**(各步幂等:load 可重复、cp 覆盖、up -d 幂等)。v6.11.0 起失败会
    记入部署历史(可复盘),取消入口对所有发起路径可用。
57. 开机自启(第二十九批 S1):**状态真值在注册表**(`HKCU\...\Run\DockerDeploySSH`),
    配置里的 `autoStart` 只记「上次意图」—— 用户可能在「任务管理器 → 启动」里禁用,
    故设置界面显示的是**系统实况**。仅 Windows;写注册表失败会明确报错(不静默)。

52. 迁移**不改项目名**:归档内 `manifest.json` 的 `project` 字段原样搬运,故目标侧回滚归属校验仍通过;但若用户期望改名,需手工处理(与 `文件映射` 的本机路径一样,迁移不触碰本机侧配置)
53. **后端 `commands::deploy_batch` 是未接入的遗留实现**(阶段七最初的后端编排:事件驱动、`deploy-batch` 事件、`[服务器名]` 日志前缀、不落断点)。批量部署实际由前端 `ui/deploy.js` 的队列完成,该命令**无任何前端调用点**。保留它会持续误导排查方向(同名命令 + 同族事件),删除又需确认无隐藏依赖,故当前显式标注并保留;改动批量行为一律改前端队列
54. 模态出场动画依赖 `transition-behavior: allow-discrete`(Chromium 117+)。**不支持时会优雅降级为瞬隐**(与改动前一致),不会白屏或卡死,但也没有出场动画 —— 此时入场动画仍生效(由 `animation` 提供,不依赖该特性)
55. **忙碌态步进条只表示「进行中」,不表示进度**:镜像迁移、卷导出等长任务的实际进度仍以日志行为准(后端不回传百分比)。按钮文案已给出阶段语义(如「预检中…」「迁移中…」)
56. **输入框只读态在暗色下靠左缘灰标区分**:`--ark-paper-dim`(#101416)与 `--ark-surface`(#0d1113)仅差 3 个色阶,底色差本身肉眼不可辨。若后续调整这两个 token,须重新确认只读态的可辨性;`:focus` 的左信号条靠**源码顺序**压过只读灰标(两者特异性相同),重排样式可能静默丢失焦点提示
57. 表单的**失焦校验**(第十三批接入):`window.bindFieldValidation(formRoot, rules)` 把一份规则清单同时接到失焦校验与提交期整体校验(同源,避免「失焦说合法、提交说非法」两套判定漂移)。**仍不做输入即校验** —— input 只清除本字段已有错误、不新增;中文输入法组合期的按键校验成本高,这是保留的取舍
58. 表单**已引入原生 `<form>`**(第十三批,5 处:服务器/项目/通知/迁移/单镜像回滚):`window.beginForm(container, labelId)` 把模态内容渲染进 `<form novalidate>` 并带 `aria-labelledby` 指向模态标题(AT 里是可命名的表单边界)。`novalidate` 抑制原生校验气泡(文案由本项目的字段级错误承担);**`submit` 恒 `preventDefault` 是必须的保险** —— HTML 规范里「可阻塞隐式提交的字段恰好一个」时 Enter 会自行提交,单镜像回滚视图恰好只有目标引用一个文本输入,不接管会导致 WebView 导航。Enter 提交另由 `window.bindFormEnter` 显式接线(仅单行文本 `input`、判 IME 组合、不越过二次确认)
59. 必填标记是**视觉 + 无障碍双轨**(信号青方块 + `.sr-only` 文本「(必填)」)。引入 `<form>` 后**仍未使用 `required` 属性**:条件必填字段(私钥路径 / 登录密码 / 启用邮件时的 SMTP 组)在未激活分支上加 `required` 会给 AT 错误预期;恒必填字段的语义已由 `.sr-only`「(必填)」承载,故维持现状
60. **Enter 提交的边界(第十三批,刻意为之)**:部署页与批量部署模态**不绑 Enter**(前者文本输入只有可选的版本标题/说明,Enter 触发「开始部署」风险不对等;后者是多台部署);回滚模态的 Enter 只走到「执行回滚」按钮(打开二次确认视图),**确认视图内不注册 Enter,故 Enter 永远越不过确认那一步**;textarea 一律保留换行语义(版本说明 / 收件人 / pre-post 钩子)
61. **失焦校验的呈现闸门(第十三批)**:必填类错误只在「表单已提交过一次」或「该字段被填过又清空」时提示,否则 Tab 扫过一张空表会满屏标红;格式类错误(端口越界 / 路径非绝对 / URL 前缀)恒提示。失焦失败**只做字段级提示** —— 不 toast、不滚动、不写顶部聚合框
62. **文字样式两处刻意例外**:① `.manage-table` 表内幽灵按钮 11px 是 12.5 基准上的再压缩(表格列宽紧张),不是漏改;② `.manage-terminal` 的 12px/1.5 与 `manage.js` 打开终端时的字符量测**硬编码耦合**(resize 上报按列数折算)—— 改其字号/行高必须同步改量测常数,否则终端宽度错位。另:`.form-label`(.02em)与 `.preset-chip`(.04em)字距低于微标签契约区间,前者是中文主体标签(不进微标签轨),后者是方案未列的既有数据件,均未动
