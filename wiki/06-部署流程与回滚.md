# 06 — 部署流程与回滚

两条管线的逐步语义。实现集中在 `commands.rs` 的 `run_one_deploy`(单镜像)/ `run_one_deploy_stack`(整栈,阶段六自 `run_deploy*` 拆出内层以复用于单发/批量/续传);共同骨架在 `spawn_deploy_task`(单发入口)与 `run_batch_deploy`(批量编排,阶段七)。

## 共同骨架

```
命令同步返回 Ok ──▶ tauri::async_runtime::spawn ──▶ CatchPanic 包裹(panic→deploy-done failure)
                                                     单发路径 deploy-done 恰好一次
取消:DeployState.cancelled(AtomicBool);开始时重置;步骤边界/打包上传循环逐项/
     exec 输出行回调/末尾复查处检查 → Err("部署已取消")
密码:resolve_password(Key→None;Password→password_plain 优先,否则 DPAPI 解密 password_enc)
中止:任一步失败 → 停止后续步骤,emit deploy-done{success:false,message:中文错误}
     (单发路径;批量路径每台以 deploy-batch 表达,不发 deploy-done)
断点:单发路径每步边界落盘 resume-deploy.json(见「部署断点续传」节)
```

**三种执行形态共享同一管线内层**(阶段六/七):单发(deploy/deploy_stack,全量事件+落断点)、续传(deploy_resume_start,同单发但从 step_next 起幂等续跑)、批量(deploy_batch,逐台串行,事件与断点关闭)。

## 单镜像管线(deploy,5 步)

| 步 | 动作 | 细节 |
|---|---|---|
| 1 打标签 | `use_date_tag=true` 时:`make_deploy_tag` 生成 `repo:YYYYmmdd-HHMMSS`;本地已存在同名 tag → sleep 1s 重生成,最多 5 次;`tag_image`。false 时沿用原 tag | 日期 tag 是"版本档案";回滚能力的来源 |
| 2 导出压缩 | **智能传输判定(前置,阶段一)**:`skip_unchanged` 开且非日期标签模式 → 建连取远端 `docker images --no-trunc` 完整 64 位 ID,与本地 `image_id_by_ref`(同口径)比较(`same_image_id`:剥 `sha256:` 前缀忽略大小写)——一致 → 跳过导出/上传/装载(判定连接保留复用到步骤 3;远端不存在/取不到 ID 回退全量);日期标签模式自动跳过检测(全新 tag 必有变化)。未跳过时:`image_size` 预检(临时盘 ≥ 镜像×1.5);`save_gzip` → `temp_dir/<uuid>.tar.gz`(TempFileGuard 守卫);进度按 5MB 节流发日志。**导出的是日期 tag 那份**(勾选时) | |
| 3 上传镜像 | SSH 建连(跳过路径复用判定连接)→ `sftp_upload` 到远端 `/tmp/`(进度按 10% 发日志;续传形态按远端已传字节断点续传);随后同步项目文件，并将本地 compose 上传为远端 `docker-compose.yml`(+`.env`/override) | 本地 Windows 路径不进入远端命令 |
| 4 装载 | `docker load -i '/tmp/<file>'`(600s,输出转发;跳过路径整步跳过;**续传形态下 load 前比对远端镜像 ID,已装载则跳过**);**勾选日期标签时追加 `docker tag <日期tag> <原引用>`**(60s)——把 compose 引用的原 tag(来自 `req.image`)也指向新镜像,否则 compose 变更检测失效、容器不重建。旧镜像变悬空,历史日期 tag 留在服务器上成为按版本回滚点 | |
| 5 启动 | `cd '<remote_dir>' && docker compose -f '<remote_compose>' up -d`(600s) | 本地 compose 使用 `<remote_dir>/docker-compose.yml`;旧远端路径配置继续兼容 |
| 收尾 | 删远端 /tmp tar;本地 tar 由 Drop 守卫删(断点期保留);**成功删部署断点**;deploy-done 后写历史 + webhook + `notify::fire` 通知 | |

## 整栈管线(deploy_stack,6 步)

前置(步骤 1 内):services 非空;Local 类 image 非空;project/server 存在;compose 副本存在。

**智能传输行为矩阵(阶段一,均缺省 false)**:

| skip_unchanged | force_archive | 未变化服务的行为 |
|---|---|---|
| false | false | v4.6.0 原行为:全量打包/上传/装载(逐字节一致) |
| true | false | 跳过打包/上传/装载(全未变化时三步全跳);manifest 条目 `file=null` |
| true | true | 仍打包上传进发布目录(供回滚 `docker load`),**仅跳过装载** |
| false | true | 等价全量(无未变化判定,自然全部装载) |

| 步 | 动作 | 细节 |
|---|---|---|
| 1 分类确认 | 校验+进度起点 | 分类来自前端确认后的 services(用户可改,可"保存为默认") |
| 2 打包 | 智能传输判定:建连查远端各服务镜像完整 ID vs 本地同口径比对;未变化服务按矩阵过滤;Local 类逐个 `image_size` 求和 ×1.5 磁盘预检;并行 save_gzip(并发 3);**续传形态本地 tar 存在且大小匹配则复用,不匹配重跑导出** | 大小取不到(镜像不存在)→ 跳过预检,save 阶段报错 |
| 3 上传 | 远端建 `<remote_dir>/releases/<yyyymmdd-HHMMSS>/`(**续传形态复用断点记录的发布目录**,不新建);compose 副本上传为远端 `docker-compose.yml`(+.env);逐包 sftp 上传到 releases 目录(force_archive 的未变化镜像包也归档;续传形态按远端已传字节断点续传);sync_files 传文件映射 | **tar 不进 /tmp,直接进 releases——留档即回滚点** |
| 4 装载 | 逐包 `docker load -i '<releases>/<包>'`(600s);force_archive 归档的未变化镜像 ID 已在远端,仅归档不装载(**续传形态 load 前比对远端镜像 ID,已装载的包跳过**) | |
| 5 拉取 | Pull 类非空:`cd '<remote_dir>' && docker compose -f docker-compose.yml pull <services...>`(900s);失败→报错提示"检查服务器能否出网,或把这些服务改为本地传输"。Pull 空→跳过 | |
| 6 启动 | `cd '<remote_dir>' && docker compose -f docker-compose.yml up -d`(900s) | |
| 收尾 | **写回滚资料(尽力而为,失败仅告警)**:compose 副本 sftp 归档进发布目录 + `manifest.json`(base64 经远端 exec 解码写入;`{ project, ts, compose_copy: "docker-compose.yml", images: [{ service, tag, file }] }`,跳过未留档的服务 `file=null`);DeployRecord 落 `release_dir`;releases 只保留最新 5 份(`ls -1dt … | tail -n +6 | xargs -r rm -rf`,失败仅告警);本地 tar 全删;**成功删部署断点**;deploy-done 后写历史 + webhook + 通知中心 fire | |

## 生产加固增补(v0.4.0+,两条管线通用)

| 增补点 | 时机 | 语义 |
|---|---|---|
| 远端磁盘预检 | SSH 建连后、上传前 | `docker info` 取 DockerRootDir → df 剩余 ≥ 镜像需求×1.5;取不到告警跳过(BusyBox 兼容性已知) |
| 断点续传 | 镜像包上传失败时 | 同路径 2s 后自动重试一次(仅同 attempt 同路径触发;文件映射不续传) |
| 并行打包 | 整栈步骤 2 | 并发 3 的 save+gzip;每完成一个检查取消;磁盘预检打包前一次性 |
| pre 钩子 | 上传完成、装载之前 | `cd <remote_dir> && ( <用户命令> )` 600s;**失败中止部署**(旧容器未动) |
| 原标签同步 | 单镜像 load 后 | 勾选日期标签时 `docker tag <日期tag> <原tag>`(见下) |
| 健康检查 | compose up 之后 | `health_wait_secs>0` 时轮询 `compose ps --all --format json`(5s 间隔):全部 running 且健康→通过;exited≠0→立即失败;exited=0→继续观察;失败附 `logs --tail 50` 并中止 |
| post 钩子 | 健康检查通过后 | 失败仅告警,不影响部署结果 |
| 部署历史 + webhook + 通知 | deploy-done 之后 | 写 `config/deployments.json`(200 条上限);`notify_webhook` 配置时 POST JSON(10s,URL 脱敏落日志);**通知中心 `notify::fire`(阶段二)**按事件订阅分发桌面/邮件(异步,失败仅日志) |

## 部署断点续传(阶段六)

单发部署(单镜像/整栈)的**每个步骤边界**把进度落盘到 `config/resume-deploy.json`(`ResumeCheckpoint`:键 `server_id|project_id|mode`、`step_next`=失败步骤号、`artifacts`=该模式结构的产物 JSON)。同一服务器+项目的单镜像与整栈断点互为不同键并存,最多 10 条(超限裁最旧)。

- **写入/清除时机**:每步完成收尾落盘;**成功**→清理产物+删断点;**取消/失败**→保留断点(断点期本地 tar 由守卫保留不删);同键**新部署覆盖**旧断点;批量部署不落断点
- **续传**(`deploy_resume_start`):校验断点与服务器/项目仍存在 → 走与正常部署**完全一致**的 spawn 路径(事件/部署历史/通知零特殊处理),管线从 `step_next` 起对已完成产物幂等化复用:
  - 本地 tar 存在且**大小匹配** → 复用(不匹配 = 产物失效,重跑导出)
  - 远端 tar 经 `sftp_stat_size` 取已传字节**断点续传**(不重传)
  - load 前比对远端镜像 ID,**已装载则跳过**(load 天然幂等,此为提速)
  - compose up 天然幂等
- **放弃**(`deploy_resume_discard`):删断点 + 本地临时 tar + 尽力删远端产物(单镜像 `/tmp` tar;整栈本次的部分发布目录;连接失败忽略不报错)
- 整栈特有:断点记录发布时间戳,续传**复用同一 `releases/<ts>/` 目录**(不新建,防半成品目录堆积)

## 多服务器批量部署(阶段七)

04 页「批量部署」→ 服务器多选 → `deploy_batch` 后台任务**逐台串行**执行与单发完全一致的管线(仅替换 server_id):

- **每台独立**:环境预检(失败计该台 failed 不中断)、部署历史(可逐台回滚)、通知(按单发语义);智能传输天然 per-server 判定;断点 checkpoint 按服务器+项目独立(但批量本身不落断点)
- **事件**:每台开始/成功/失败/跳过 emit `deploy-batch`;**不发** deploy-progress/deploy-done;deploy-log 每行加 `[服务器名] ` 前缀进共享日志区
- **取消**:「停止批量」→ `cancel_deploy` → 当前台由管线取消检查中止(计入 failed,message=「部署已取消」),余台循环顶部逐台 emit skipped;结束追加 `batch-done` 汇总条目
- **互斥**:批量期间锁定模式/服务器/项目选择;部署进行中亦不可发起批量;服务器配置缺失只影响该台(emit failed),不中断批量

## 一键回滚(应用内,阶段一)

04 部署页「部署历史」每条记录的操作列「回滚」按钮 → 回滚模态(列表 → 确认 → 执行三视图):

- **整栈记录** → `rollback_list_releases` 列出该项目服务器的历史发布(新 → 旧;展示各发布含的服务与镜像包数;旧版本发布无 manifest 时优雅降级仅列文件)→ 选中 → 确认 → `rollback_execute_stack`:
  1. 校验发布目录存在;读 manifest 并**留档归属校验**(manifest.project ≠ 当前项目即中止,防误回滚共用 remote_dir 的其他项目留档)
  2. 逐包 `docker load`(自动恢复镜像原标签;**部分失败时明确提示已装载 x/y 个包、镜像标签已恢复但容器未重建**,可排除问题后重发)
  3. 恢复 compose 副本(无副本沿用服务器现有文件,警告继续)
  4. `compose up -d` 重建(override 文件链与部署时一致)
- **单镜像记录** → 从记录 images 取 repository → `rollback_list_tags` 列历史标签(创建时间倒序)→ 选日期标签 + 填目标引用 → `rollback_execute_single`:校验 `repo:dateTag` 在服务器存在(不存在明确报错——该版本镜像未留档且已被清理的兜底)→ `docker tag` 零拷贝重指 → `compose up -d`
- 执行期复用 deploy-log / deploy-done 事件(模态内日志镜像,主页同步);成功落 `mode="rollback"` 部署历史;**rollback 记录不可再回滚**(灰 — 防回滚链);通知中心按 success/failure/cancel 分发
- **回滚三级判定**(对应部署时智能传输的三种留档形态):①镜像包在 → `docker load` 恢复;②包未留档但镜像 tag 仍在服务器(跳过未变场景的常态)→ 无需装载,up 直接用;③均无 → 明确报错

## 独立回滚中心(06 页,第三批)

上面的应用内回滚入口埋在「04 部署页 → 部署历史」里,**只能回到本应用部署过的项目**(释出目录固定取 `server.remote_dir/releases`)。06 页「回滚中心」改以**服务器真实目录**为准,任何含 compose 的目录都可回滚。

```
06 页选服务器(「扫描起点」可填 /home 等,留空用服务器部署目录)
→ rollback_scan_projects:项目 = compose 文件扫描(深度 ≤4,排除 releases/.git)
   + docker ps 的 com.docker.compose.project.working_dir label 合并去重
→ 左列项目(归档数 / 最近归档 / 运行中容器数 / 是否已配置),点选加载明细
→ rollback_project_detail:<dir>/releases 下最多 50 个归档(含 manifest 服务清单)
   + 该目录 compose 声明的各仓库日期标签(YYYYmmdd-HHMMSS,倒序)
→ 两类回滚:
   「回滚到此归档」rollback_execute_stack_at({dir, releaseTs})
     校验 <dir>/releases/<ts> 存在 → 归属校验按路径前缀(归档必须在该项目目录下)
     → 逐包 docker load → 恢复 compose 副本到 <dir>/docker-compose.yml
     → cd <dir> && docker compose up -d
   「切回此版本」rollback_execute_single(复用应用内命令,故要求该项目在软件内已配置)
→ 执行期复用 deploy-log / deploy-done(本页独立日志面板)
```

与应用内回滚的差异:归属校验从「manifest.project == 项目名」改为「归档路径必须位于所选项目目录下」——因为服务器上的目录名未必等于应用内项目名,按路径前缀判定更贴合实际且仍能防止跨项目误回滚。

## 回滚操作(手动,服务器上)

**单镜像模式(勾选日期标签部署过)**:每次部署都会在服务器上留下一个带日期 tag 的版本镜像(load 后 retag,日期 tag 保留),直接切换指针即可:

```bash
# 1. 看服务器上有哪些历史版本
docker images | grep myapp
# 2. 把 latest 指回旧版本(指针移动,零拷贝)
docker tag myapp:20260829-143000 myapp:latest
# 3. 重建容器
cd /opt/<你的项目> && docker compose -f docker-compose.yml up -d
```

**整栈模式**:依赖 releases 留档(每次部署的镜像包保留最近 5 份):

```bash
# 1. 看有哪些回滚点
ls -1dt /opt/<你的项目>/releases/*/
# 2. 把想要的旧镜像包装载回去(覆盖同名 tag)
docker load -i /opt/<你的项目>/releases/<时间戳>/<包名>.tar.gz
# 3. 重启栈
cd /opt/<你的项目> && docker compose -f docker-compose.yml up -d
```

若不使用应用内一键回滚,上述手动方式仍然有效(一键回滚即这些步骤的封装)。

## 环境检测闸门规则

| 层 | 未通过的后果 | 入口 |
|---|---|---|
| 宿主机 | `AppState.hostOk=false` → 镜像列表/部署向导导航灰置不可进;服务器管理页可进(黄条提示)但部署动作会被后端再拦 | `host_check` / 检测页 |
| 服务器 | 部署向导开始部署前强制 `server_env_check`,任一项未通过 → 阻断 + 跳转按钮 | `test_server` / 服务器页 |
| 部署中 | 后端仍会再验(打包磁盘 ×1.5、Local 镜像存在性等) | 双保险,前端非唯一防线 |

## 已知的时序/边界行为

- 取消是协作式:导出/SFTP 大文件传输中不中断,在步骤边界或 exec 输出行时生效 → UI 有"将在当前步骤结束后生效"提示(取消后断点保留,可从步骤 N 续传)
- `deploy-done` 成功与"最后一步后瞬间取消"存在极小竞态窗口(与单镜像管线一致,已知可接受)
- Local 类镜像本地不存在:预检阶段(打包)由 `docker save` 报错;更早的拦截靠前端匹配徽章(✗ 本地不存在)
- releases 时间戳精确到秒:同秒内并发两次整栈部署会同目录混包(单用户桌面场景,可接受)
- manifest.json / compose 副本写入是**尽力而为**:失败仅告警,不推翻已成功的部署;缺失时回滚命令优雅降级(列表无服务名、回滚沿用服务器现有 compose)
- 智能传输跳过判定依赖远端 `docker images --no-trunc` 与本地 `docker image inspect` 同为完整 64 位 ID 口径(常量 `REMOTE_IMAGES_CMD_FULL` 有注释与回归单测锁定);远端取不到 ID 时保守回退全量传输
- 回滚到「跳过未留档」的服务依赖其镜像 tag 仍在服务器(跳过即"未变化"的前提);镜像被清理后该路径由 execute_single 的存在性校验/`compose up` 报错兜底

## compose 默认镜像名兜底扫描(v0.4.3 起)

服务有 `build:` 但未写 `image:` 字段时(compose v2 会把构建产物命名为 `<项目目录名>-<服务名>`),解析阶段自动按以下候选扫描本地镜像并回填:

1. compose 顶层 `name:`(若写)
2. **原始 compose 目录名**——导入时记录在副本目录的 `origin.json`,不受副本迁移影响
3. 副本/原始路径的父目录名(最后手段)

- 命中:镜像自动填入(多 tag 优先 `latest`),匹配状态=精确匹配,warning 提示"建议在 compose 中显式写 image: 固化命名"
- 未命中:保持"本地不存在",warning 列出已扫描的候选名(uuid 形态的内部目录名不展示)
- 纯函数与副本结构(uuid 目录 + origin.json)均有单测覆盖
